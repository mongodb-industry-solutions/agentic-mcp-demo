❔ Help — how to drive this demo
Five demos, each one can be driven on its own · Intent-Based Networking (IBN) · What-if scenarios (DTW network digital twin) · Green networking · OTA downloads · Connected rides

The shell is a multi-agent orchestrator. Every query is routed in two stages — a domain classifier picks the demo (IBN or DTW), then Atlas Vector Search picks the MCP service inside that domain — and the matching domain agent runs its own ReAct loop over that domain's tools. Watch the Agent Log on the right to see routing, tool calls and results as they happen, and the Workstreams tab to see the agent's running memory of each thread.

Both opener queries are pre-loaded in the input history: press ↑ once for the IBN opener, twice for the DTW opener. Below, click any prompt to copy it.

1 · Intent-Based Networking

A retail customer asks for connectivity in business language. The agent turns that sentence into a structured intent, checks it against real inventory, activates a plan, then watches it break under load and repairs it.

IBN — intent → feasibility → activation → violation → repair
Services: ibn_intent · ibn_inventory · ibn_feasibility · ibn_assurance · ibn_telemetry_simulator
1

What happens: the IBN agent extracts the fields from free text — site, SLOs, segmentation and timing — and submits a structured intent. The new intent appears on the IBN dashboard immediately (Change Streams).

2

What happens: the intent is matched against sites, resources and topology; geospatial lookup finds nearby spare capacity. You get a verdict with the gaps that block it.

3

What happens: a plan is proposed and then activated — policy snapshots are written and the intent moves to active on the dashboard.

4

What happens: the telemetry simulator pushes a burst of load into the time-series collection, breaching the 40 ms POS latency objective. A compliance violation lights up on the dashboard.

5

What happens — the hero query: one $vectorSearch stage combines semantic similarity over the knowledge base with structured pre-filters on kind, a time window, and a geographic bounding box. Semantics + time + geo + exact match, inside a single index. In ?mode=eng the dashboard shows the raw aggregation pipeline.

6

What happens: the recommended remediation from the retrieved runbook is applied, the template version is bumped, and compliance returns to green.

IBN — self-healing: nobody types the diagnosis
Keep the IBN dashboard open: the SLO monitor that detects the breach runs there
7

What happens: live telemetry plays on a compressed 08:55–10:05 clock. Nothing declares a violation: the monitor computes the p95 latency every 2 seconds and opens an incident after three breached windows. Then the IBN agent takes over without a prompt: a 🤖 Self-healing panel appears in the chat, and the agent runs the hero query and checks the autonomy envelope. At autonomy L3 (the default) it stops at a recommendation; say apply runbook to decide as the NOC. The dashboard's Self-healing loop panel shows each stage and the MTTR clock.

8

What happens: the store you repaired in step 6 gets the same rush and stays green: the telemetry reads the store's live configuration, so the fix holds on data, not by script. Where autonomy L4 is enabled (the Agent Engine twin), the agent also applies the runbook itself, the monitor verifies the recovery, the repair becomes a new precedent in the knowledge base, and the sister stores get a canary proposal that waits for the NOC.

2 · What-if scenarios (network digital twin)

A digital twin of ACME Mobile's plans, QoS profiles, RAN/core topology and traffic models lives in Atlas. The agent runs simulations against it, so you can ask "what breaks if…" before touching production.

DTW — scenario → refinement → simulation
Services: dtw_plan · dtw_topology · dtw_traffic · dtw_scenario · dtw_simulation
1

What happens: the DTW agent extracts plan, target rate, markets and time window, resolves the numeric rate to the nearest QoS profile (with an explicit substitution note), and creates a what-if scenario. It shows up on the DTW dashboard.

2

What happens: a short follow-up updates the existing scenario in place rather than creating a new one — this is the conversation memory and domain stickiness at work.

3

What happens — the hero query: a $graphLookup walks the dependency tree from the plan through QoS → cells → eNodeBs → SGW → PGW to establish scope, per-cell load is projected from the traffic models, and a hybrid $vectorSearch retrieves analogous past incidents and their mitigations — all in one tool call. Graph for operational structure, vector for institutional memory, one database.

3 · Green networking (night shift)

The 🌙 Night shift button in the banner opens a map of the Midtown Manhattan radio network, scenario Night shift. As offices empty, the network puts idle 5G capacity carriers to sleep; the coverage layer always stays on. No shell prompts: press ▶ Play and narrate. The map is drawn from the network's documents in Atlas; the night is simulated in the page.

Night shift: sleep → unplanned spike → reflex → resume → lesson
Page: /night · same session token as the shell
1

18:00 to 01:00, the tide goes out

Offices empty; the agent's 15-minute check puts idle capacity carriers and small cells to sleep. Power falls against the always-on line; every service promise holds (the hospital slice never sleeps).

2

01:10, the train

A subway disruption sends crowds up at Penn Station, where carriers sleep. Within minutes the deterministic reflex wakes them, one sector at a time: the energy saving stops right away where it has to.

3

02:30, back to sleep

Once most people are home, the saving resumes and the agent stores the lesson. The night ends at about 29% less power.

4

Hero queries → Run it on Atlas

"Can this carrier sleep?" runs live on Atlas for the current minute: inventory, p95 of the 3GPP counters, the forecast, the coverage relation ($graphLookup) and the service promises in one aggregation. At 01:30 Penn Station shows 85% measured load against a 10% forecast: not safe.

4 · OTA downloads (robotaxi fleet)

Same network, the Tuesday afternoon before. An anonymized robotaxi operator asks before pushing a 2.4 GB update to 300 cars. Open 📦 OTA downloads in the banner (or pick Scenario: OTA downloads in the map), then press ▶ Play (13:00 to 17:00).

OTA: request → per-vehicle answer → NOC review → paced and deferred downloads → done
Page: /ota · hover a robotaxi for its answer, click it to quote it on Atlas
1

13:00, the fleet asks

The fleet console sends the campaign: 300 cars, 2.4 GB each, done by 18:00, keep 5 Mbit/s per car for remote assistance.

2

13:01, one answer per vehicle

169 cars download now, paced so no cell passes 80% for retail users. 131 sit in congested cells: the network answers "not now" with a menu of cheaper cells nearby, and the fleet picks the one each car's next ride ends in (the arcs). The network never sees the rides. Hell's Kitchen is not offered: its radio is quiet, but the backhaul behind it is full.

3

13:02, NOC review

Above 100 vehicles the campaign waits for the NOC; approved at 13:04.

4

15:30, revised offers

The rush turns the cells of 34 waiting cars congested: the network revises their offers, a change stream delivers them, and the fleet picks again. All 300 are done by 16:19, before the deadline; nothing was delivered in congested cells. In Hero queries → Revised offers, live this runs on Atlas: press Run, stop the consumer halfway, resume from its token, and every event arrives once.

5

Hero queries → Run it on Atlas

"Quote one vehicle" runs live: $geoNear for the cells near the car, the p95 of live counters, $graphLookup over the backhaul, the tier rule. The fleet gets tier and Mbit/s, never the raw load.

Interleaving the IBN and DTW flows

Each of the five demos stands on its own. IBN and DTW are driven from the shell: separate domains, separate agents, separate collections, separate workstreams. You can switch between them mid-session and each thread keeps its own state — start the IBN intent, jump to DTW, come back and continue with propose and activate.

One caveat. The short follow-up steps (feasibility check, propose and activate, change to 20 Mbps, diagnose violation, apply runbook, run simulation) carry no domain of their own — they are resolved against the previous turn. If you have just switched demos, name the target explicitly (IBN: feasibility check, DTW: run simulation) so the classifier lands in the right domain. Sequences within one flow are safe to keep short.

Controls in the header

  • ↺ Reset demo data — drops and re-seeds this session's IBN + DTW demo collections and clears the agent-state planes (workstreams, memories, preferences, routing decisions). Shared read-only fixtures and the service/agent catalogue stay put. Use it to get back to a clean slate between runs.
  • 📊 IBN dashboard / 📊 DTW dashboard — open in a second window; both are bound to your session token, so they mirror your own isolated demo lane. Append &mode=exec for the narrative, non-technical rendering, or leave it out for the engineering view with raw pipelines.
  • 🌙 Night shift / 📦 OTA downloads / 🚕 Connected rides (Agent Engine shell) — the network map's three scenarios, each a demo on its own and bound to your session like the dashboards; the menu in the map's header switches between them. The agents acting on these scenarios come in a later version: today they are played back in the page, with their queries live on Atlas.
  • Agent Log · MCP Servers · Workstreams tabs on the right — live routing/tool trace, the auto-discovered service registry (you can add a new MCP server at runtime), and the agent's per-thread memory.

Typing status or preferences in the shell prints the session's registry state and learned user preferences.
